# Demo Mode Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A read-only "Try the demo" so recruiters can see LinkdUp without signing up: one shared demo user, sample data, every write blocked on the server.

**Architecture:** `requireAuth` hands demo-user requests to one `demoReadOnly` middleware, which refuses every non-GET/HEAD request (except logout) and the GETs that spend Google quota. `POST /api/auth/demo` signs in with server-only env credentials. Discover and more-venues answer the demo user from stored rows. The mobile app reads `is_demo` from `/api/auth/me` and shows a banner. One `api.ts` hook turns `demo_read_only` into a friendly dialog.

**Tech Stack:** Express + zod + Supabase (server, `tsx --test`), Expo / React Native Web (mobile, node:test + jest), Postgres seed SQL.

**Spec:** the slice-6b request (in the session; summarised in Global Constraints).

## Global Constraints

- `DEMO_USER_ID` (UUID) unset or invalid: demo mode is off and nothing changes. `/api/auth/demo` returns 404 unless `DEMO_USER_ID`, `DEMO_USER_EMAIL` and `DEMO_USER_PASSWORD` are all set.
- Refusal body: `403 {"error":"demo_read_only"}`.
- Copy, verbatim: banner `Demo mode, read only. Sign up to create your own parties.`, button `Try the demo`, action `Sign up`.
- Credentials are server-only: never in a response, never logged.
- No code comments, no new dependencies, no migrations, nothing inserted into auth tables, no env/Supabase/Google/DNS changes.
- One commit per step, no attribution lines.

## Review Focus

- Someone with a demo token changes the demo password or email through Supabase Auth directly. `/api/auth/demo` resets the demo credentials with the admin API and retries once (Task 2 test).
- `DEMO_USER_EMAIL` points at a real account whose id is not `DEMO_USER_ID`, which would hand out an unguarded session. Refuse with 500 `demo_misconfigured` (Task 2 test).
- A new unauthenticated write route bypasses the guard. The route-enumeration test pins the exact set of unauthenticated writes (Task 1 test).
- Background writes (hint seen, live location) pop the demo dialog uninvited. Mark them quiet in `api.ts`. The seed sets lobby locations to custom so the lobby makes no auto write (Task 4).
- Discover or swipe triggers Google lookups for the demo user. `/discover/venues`, `/discover/venues/more` and `/party/:id/more-venues` answer from stored rows (Task 1 test: Places mock call count 0).

### Task 1: Server write guard

**Files:**
- Create: `server/src/middleware/demo.ts`, `server/test/demo.test.ts`
- Modify: `server/src/middleware/auth.ts`, `server/src/routes/discover.ts`, `server/src/routes/party.ts`, `server/src/routes/auth.ts` (`/me` adds `is_demo`), `server/test/flowApp.ts` (return `app`)

**Interfaces:**
- Produces: `demoUserId(): string | null`, `isDemoUser(id: string | undefined): boolean`, `demoReadOnly(req, res, next)`.
- Rules: a non-demo user passes through. A demo GET/HEAD is allowed except `/api/calendar/oauth/start`, `/api/discover/places/search` and `/api/user/location/search`. A demo non-GET is allowed only for `POST /api/auth/logout`. `/api/health` is unauthenticated, so the guard never runs there.

- [ ] Test (boots the real app with `bootApp`, walks `app._router.stack`): every authed non-GET route returns 403 `demo_read_only` for the demo user, except logout. The same routes never return `demo_read_only` for a normal user. The unauthenticated writes are exactly `POST /api/auth/signup|login|demo` and `POST /api/schools/lookup`. Demo GETs `/api/auth/me` (`is_demo: true`), `/api/user/me/parties` and `/api/discover/venues` return 200, with zero Places calls. The three quota GETs return 403. With `DEMO_USER_ID` unset, the same user is not refused.
- [ ] Run `npm test` and check it fails. Implement. Run `npm test` and check it passes. Commit.

### Task 2: Demo sign-in

**Files:** Modify `server/src/routes/auth.ts`, extend `server/test/demo.test.ts`.

- `GET /api/auth/demo-available` → `{available: boolean}`.
- `POST /api/auth/demo` with `rateLimit(DEMO_LIMIT = 10, 15 min)` per IP. It returns 404 when not configured. On a failed sign-in it calls `supabaseAdmin.auth.admin.updateUserById(demoId, {email, password, email_confirm: true})` and retries once. A session user id that is not `DEMO_USER_ID` gets 500 `demo_misconfigured`. It returns the same shape as `/login`.
- [ ] Tests: 404 when unset; returns a session; the response body never contains the password; the reset-and-retry path; the misconfigured id; 429 after `DEMO_LIMIT` hits. Commit.

### Task 3: Seed SQL and images

**Files:** Create `server/src/db/seed/demo_seed.sql` and `mobile/public/demo/*.jpg|png` (generated locally with PIL; the generator script is not committed).

- 6 placeholder ids sit in one temp table at the top (demo + 5 friends). A guard raises an error if any of them is missing from `auth.users`, because of the `users_auth_fk` foreign key. Every row id uses the `de3000..` prefix. Parties are `Demo: ...` with codes `DEMOA1`, `DEMOB2`, `DEMOC3`, place ids are `demo-...` and photos are `/demo/...`. The whole file is idempotent: `on conflict` everywhere, all in one transaction.
- Parties: Trivia (waiting), Brunch (swiping, `current_card_index` 2), Rooftop (locked with a Link and a locked date).
- [ ] Commit.
